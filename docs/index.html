과자 옮기기 로봇 문서 가이드

처음 합류한 팀원이 흩어진 문서를 빠르게 이해하도록 요약한 페이지입니다. 기준 문서는 설계 문서(2026-10-22 chat-ui-design)이며, 다른 문서와 충돌하면 설계 문서가 우선합니다.

1. 한눈에 보기

SO-ARM101 로봇팔이 여러 과자가 섞인 트레이에서 목표 과자(지금은 오란다, config.target.name으로 바꿀 수 있음)만 골라 빈 트레이로 옮긴다. 사람이 채팅이나 음성으로 작업을 시키면 일을 시작하고, 몇 번 하면 지쳐서 dori_dori(도리도리)로 일을 거부한다. 진행자가 달래거나 r 키를 누르면 다시 일하고, 마지막 과자를 옮기면 완료 멘트 후 IDLE로 돌아간다.

하드웨어는 SO-ARM101 팔로워 1대·학습용 리더 1대, 카메라 3대(tower · side 외부 2대 + follow 손목)이고, 2일 해커톤 프로젝트다. 시연 노트북은 Windows 11 PC이고, 화면은 카메라 3칸 + 3D 디지털 트윈의 4분할이다 (2026-10-23 실기를 시작했다).

2. 시연 흐름

  1. 진행자가 "이 로봇은 과자 공장 직원입니다. 오란다만 골라내요."라고 소개하고, 채팅에 "과자 옮겨줘"를 입력한다 (s 키도 같은 동작). 상태 IDLE → WORKING.
  2. 시작할 때 코드가 전체 개수 N을 정한다 (첫 개수 세기 성공 값 → 없으면 채팅의 "5개" → 없으면 target.initial_count). 로봇은 한 개씩 옮기면서 점점 투덜대고, 거부 직전 한 번은 지쳤다는 대사를 한다.
  3. 전체의 절반(올림)을 옮긴 뒤(3→2, 4→2, 5→3, 6→3개째) 코드가 dori_dori를 작업당 한 번 강제한다. 로봇이 도리도리하며 거부하고 상태는 REFUSING. 전체가 1~2개면 거부 없이 끝까지 한다. 옛 고정 임계값(3·6)은 decision.refuse: fixed.
  4. 진행자가 "조금만 더 해 주세요~"라고 달래거나(채팅·음성) UI 재개 버튼 또는 r 키를 누르면 count = 0으로 초기화되고 다시 WORKING. 한 번 달랜 뒤에는 같은 작업에서 다시 거부하지 않고 끝까지 옮긴다.
  5. 마지막 오란다까지 옮기면(남은 0개) 완료 멘트 → DONE → 자동으로 IDLE. 트레이를 다시 세팅하면 채팅만으로 다시 시작할 수 있다.
  6. 이상 시 space 또는 UI 비상정지 → ESTOP, 해제는 restart(home_pose 복귀 후 IDLE).
  7. 대기 중에는 화면 아래 스킬 테스트 줄(오란다 1회 · 모델 도리도리 1회 · 코드 도리도리 1회 · 홈으로)이나 "도리도리 해 봐"로 동작 하나만 1회 실행해 볼 수 있다 (TESTING 상태).
시연 직전 체크, 장애 대응, 발표용 숫자는 DEMO_RUNBOOK.md에 있다.

3. 핵심 규칙 (CLAUDE.md의 절대 규칙 9개)

#규칙왜
1횟수는 코드가 센다. LLM은 프롬프트로 받은 숫자를 해석만 한다.피로도·거부 타이밍이 시연의 핵심이라 LLM의 변덕에 맡기지 않는다.
2ACT 정책 하나 = 동작 하나. 순서·횟수는 controller가 관리한다.ACT는 기억이 없어 몇 번째인지 모른다.
3LLM 출력은 허용된 값만. skill은 oranda_pickup | dori_dori | done, 채팅 intent는 상태별 허용 목록(start_task | chat | resume | dori_dori) 안에서만. 벗어나면 규칙으로 결정. dori_dori(도리도리 1회)는 대기 상태에서만.잘못된 출력이 로봇 동작으로 이어지지 않게 한다.
4STT는 UI 🎤 누르고 말하기. 인식 문장은 채팅과 같은 경로(controller.chat).상시 청취는 발표장 소음·모터 소리·로봇 자신의 TTS 때문에 부정확하다. 같은 경로면 로직을 재사용한다.
5파인튜닝 없음. 개수 세기는 학습 없이 OpenCV 규칙으로 한다(VLM은 계획만 했고 학습하지 못했다).2일 안에 끝내야 해서 개수 세기는 학습 없이 간다.
6physicalai / LeRobot 코어 수정 금지. 설치된 버전의 API를 확인해 그대로 사용.라이브러리를 고치면 유지가 어려워지고, 시그니처가 버전마다 다를 수 있다.
7oranda_pickup ACT는 놓기까지만. 그리퍼 "닫힘 → 열림"을 감지하면 ACT를 멈추고 코드가 lift_pose → home_pose로 복귀. 스킬 시작 전에는 항상 home_pose.복귀 구간은 매번 궤적이 달라 데이터가 적을 때 노이즈가 되고, "돌아오자마자 또 집으러 가는" 혼란도 막는다.
8외부 API는 타임아웃 필수. provider 체인이 전부 실패해도 로봇 루프는 규칙 fallback으로 계속 돈다.네트워크 때문에 로봇이 멈추면 시연이 깨진다.
9비상정지는 토크 유지. 정지 순간의 목표값을 고정해 유지한다.토크를 끄면 팔이 떨어져 과자·트레이와 부딪힌다.

4. 구조

모든 명령은 project 루트에서 실행한다. 프로세스 1개로 돌며 스레드는 controller 루프, uvicorn, 콘솔 키, 카메라 캡처, 실행 기록 저장 등으로 나뉜다. 시연 노트북은 Windows라 파이썬은 .venv/Scripts/python(Git Bash) 또는 .venv\Scripts\python(PowerShell)이다.

.venv/Scripts/python -m snackbot --dry-run            # 로봇 없이 전체 흐름 + UI (http://localhost:8000)
.venv/Scripts/python -m snackbot --dry-run --no-ui    # 콘솔만
.venv/Scripts/python -m snackbot                      # 실제 로봇
.venv/Scripts/python -m snackbot.vision tests/samples/tray_3.jpg   # 모듈 단독 테스트 (--blobs: ROI·면적 맞추기)
.venv/Scripts/python -m tools.robot_probe save home   # 현재 팔 자세를 home_pose로 (lift도 동일)
.venv/Scripts/python -m snackbot.robot home           # 스킬 하나만: home | dori_dori | dori_script | oranda_pickup
.venv/Scripts/python -m pytest                        # 487개
의존 방향: server → controller → (brain, vision, skills, voice). controller는 FastAPI를 모른다. --no-ui면 server 없이 돈다. 실제 로봇이면 skills 자리에 robot.py의 RobotSkills가 들어간다.

상태 머신

stateDiagram-v2
    [*] --> IDLE
    IDLE --> IDLE: 잡담 → 캐릭터 대답
    IDLE --> WORKING: start_task (채팅 · 음성 · s 키)
    WORKING --> WORKING: 옮기기 성공 (count + 1) / 실패 재시도 (1회)

    WORKING --> ESTOP: space · UI 비상정지
    REFUSING --> ESTOP: space · UI 비상정지
    ESTOP --> IDLE: restart (home_pose 복귀 후)
    IDLE --> TESTING: 스킬 테스트 버튼 · 도리도리 해 봐
    TESTING --> IDLE: 1회 끝 (결과 한 줄)
    TESTING --> ESTOP: space · UI 비상정지
상태채팅 허용 intent처리
IDLEstart_task, chat, dori_doristart_task → 시작 개수 정하고 사이클 시작. dori_dori → 대사 소리 시작 뒤 도리도리 1회 (TESTING)
DONEstart_task, chat완료 멘트 후 자동으로 IDLE
WORKINGchat, (phase=waiting_operator일 때) resume대답만, 작업 영향 없음. waiting_operator에서 resume → 같은 오란다를 다시 시도 (count 불변)
REFUSINGresume, chatresume → count = 0, WORKING (거부는 작업당 한 번이라 다시 거부하지 않는다)
ESTOP / TESTINGchat대답만. ESTOP 해제는 restart 명령으로만. TESTING 중 작업 지시·s·r은 거부
  • phase(UI 표시용, WORKING 내부 단계): idle | counting | thinking | speaking | acting | returning | waiting_operator
  • 옮기기 실패가 max_retry(기본 1)를 넘으면, 즉 같은 오란다를 두 번 연속 놓치면 투덜대는 대사(채팅 + TTS) → 소리가 시작되면 도리도리 1회 → WORKING을 유지한 채 phase=waiting_operator. 횟수·피로도·작업당 거부에는 넣지 않는다. 채팅 "이어서 해줘"·🎤·재개 버튼·r 키로 같은 오란다를 다시 시도하며 count는 변하지 않는다. 비상정지는 도중에도 먹는다.
  • ESTOP 후 restart는 home_pose로 천천히 복귀한 뒤 IDLE (사람이 명시적으로 다시 시작하는 쪽이 안전). 재시작은 진행 중인 동작이 멈춘 뒤에만 받고, 접수한 순간의 세션 번호가 바뀌었으면(그 사이 비상정지) 거부한다.

왜 ACT가 과자를 찾는데도 개수를 세는가 (B → A)

찾아 집는 일은 ACT가 영상만 보고 한다. 개수 판정은 정확도 때문이 아니라 ACT가 못 하는 두 가지 때문이다: 언제 끝낼지(ACT는 "이제 없다"를 몰라 0개여도 허공이나 다른 과자를 집는다)와 성공했는지(count는 성공 때만 올라가고 이것이 거부 타이밍을 정한다).
B (개수 세기 끔)A (OpenCV 켬, 현재 기본)
시작 개수채팅의 n("3개 옮겨줘") → 없으면 target.initial_count시작 전 counter로 셈
성공 판정grasped: 닫힘 구간의 그리퍼 최솟값 ≥ grasp_min (빈 그리퍼는 끝까지 닫힘)실행 전후 개수 감소. grasped는 로그용 보조

한계다른 과자를 집어도 성공으로 셈. 시작 개수가 틀리면 끝 판단도 틀림모델·튜닝 필요
  • 현재 vision.chain에는 OpenCV counter 하나가 있어 기본이 A다. 화면의 개수 세기 토글(끔 · OpenCV)로 B로 내릴 수 있고, 지금 세기 버튼(대기 상태)으로 한 번 세어 확인할 수 있다 (횟수·피로도는 그대로). chain이 비어 있으면 항상 B. A에서 counter가 전부 실패한 사이클은 그 사이클만 B로 판정한다 (멈추지 않음).
  • UI의 vision_method: B면 estimate("추정"으로 표시), A면 실제 counter 이름. 토글 상태는 state의 vision_choice·vision_options로 온다.
  • 성공이면 count += 1. 실패는 count에 넣지 않고 실패 멘트 후 재시도(최대 max_retry회, 기본 1) → 그래도 실패(두 번 연속)면 투덜대는 대사 → 도리도리 1회 → phase=waiting_operator. 놓은 뒤 개수가 안 줄었으면 vision.confirm_s(0.7초) 뒤 한 번 더 세어 확인하고(그리퍼만 믿고 성공으로 치지 않는다), 앞 세기가 남은 개수보다 많은 값이 연속 두 번 나오면 정정한다.

채팅 의도(chat)와 키워드 fallback

채팅 입력과 STT 결과는 같은 경로(brain.chat)로 들어온다. 출력: {"intent": "start_task | resume | dori_dori | chat", "say": "...", "n": 3}. n은 "3개 옮겨줘"의 개수(없으면 null)다.

상태allowed intent
IDLEstart_task, chat, dori_dori
DONEstart_task, chat
WORKING (phase=waiting_operator)resume, chat
WORKING (그 밖의 단계) / ESTOP / TESTINGchat
REFUSINGresume, chat

JSON 실패나 허용 외 intent면 키워드 규칙: start_task(옮겨, 집어, 시작, 일해), resume(조금만, 부탁, 힘내, 한 번만, 이어서, 계속, 재개), 그 외 chat. 한 문장에 도리도리와 작업 시작이 같이 있으면 작업 시작이 먼저다 ("도리도리 하지 말고 옮겨줘"). n은 숫자 또는 한글 수사(하나·둘·셋…) 정규식으로 파싱한다.

fallback 대사 (LLM 실패 시)

준비된 대사 목록이 있다: oranda_pickup, count 3 예고, dori_dori("싫어요! 힘들어요!"), done, 실패 재시도, 연속 실패 give_up(투덜대는 대사), 재개, 잡담, 일하는 중 잡담. 목록은 DECISION_LOGIC.md 6장.

8. 로봇 연동 (physicalai 런타임)

physical-ai-studio에서 학습해 OpenVINO로 내보낸 ACT를 physicalai 0.3.0으로 실행한다 (설계 문서 11.6절). 예전 초안의 "루프 직접 작성" 대신 RobotRuntime 하나 + 동작 출처 교체(snackbot/robot.py)다. Switch.active가 PolicySource(정책 oranda_pickup / dori_dori) 또는 MoveSource(보간 이동)를 가리키고, run()마다 stop_event(비상정지 · 끝 신호)를 건다.

  • 관절 순서: shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper. 단위: 몸통 -100..100, 그리퍼 0..100 (정규화 단위). home_pose, lift_pose, 그리퍼 기준값 모두 이 단위.
  • 시작 때 정책을 로드하고 warmup한다 (실제 관절값·카메라 프레임으로 한 번 추론). 카메라 이름이 모델과 다르면 바로 안내하고 멈춘다. 모델 폴더가 없는 정책은 건너뛴다 (과자 모델 없이 home·dori_dori 확인 가능).
  • 카메라 3대(tower · side · follow)는 런타임이 모두 열고, 카메라·시리얼은 스레드 안전하지 않아 _io 락으로 보호한다. 동작 중 프레임은 런타임 캐시, 쉬는 중엔 카메라에서 읽는다. camera_map은 학습 때 이름(a, b, follow)을 config 이름으로 매핑한다. 로봇 포트는 한 프로그램만 잡으니 Studio 세션을 먼저 닫는다.
  • 정책 장치는 skills.device (시연 노트북은 CPU). 제어 주기는 30 Hz가 목표지만 실기에서 11~13 Hz가 나왔다 (12장 열린 문제).
그리퍼 정지 조건은 "닫힘 → 열림" 전이. 그리퍼 감시(Tap.on_tick, 제어 스레드에서 동기 호출)는 열림을 한 번 본 뒤부터 닫힘을 인정하고(홈에서 이미 닫혀 있어도 오작동 없음), 닫힘 기준(closed_below 56.0)을 지난 뒤 열림 기준(open_above 56.5)을 open_hold_s(0.15초) 넘으면 ACT를 멈추고, 안전장치로 max_time_s(20초)도 둔다. 실측(2026-10-23, robot_probe watch): 빈손 49.4~50.1, 오란다 쥠 54.2~55.4, 열림 79.0 → 값 유지. 멈춘 뒤 코드가 lift_pose → home_pose로 복귀한다 (poses.yaml, lift는 그리퍼를 닫은 채 저장).
비상정지는 토크 유지. 런타임을 끊지 않는다. 런타임은 정지 때 아무 명령도 보내지 않아(return_to_initial_state 기본 False) 서보는 마지막 목표를 토크 켠 채 유지한다. 비상정지마다 세대 번호를 올려, 직후 해제(재시작)가 끼어도 진행 중이던 동작은 비상정지로 끝나고 다음 단계로 가지 않는다. 재시작은 진행 중인 skills.run이 끝난 뒤에만(최대 5초). 프로그램을 끝낼 때(close)는 SO101.disconnect가 그 순간 측정값을 목표로 다시 잡고 포트를 닫는다.
  • dori_dori: skills.dori_dori.source auto | policy | script. auto는 모델 폴더가 있으면 정책, 없으면 코드 도리도리. 코드 도리도리는 홈 기준 shoulder_pan만 ±amplitude(최대 30)로 shakes번 흔든다. UI 코드 도리도리 1회 버튼은 source와 무관하게 항상 코드 동작이다 (dori_script). 실기에서 모델 도리도리는 pan이 ±1에 머물러 시간 초과라 코드로 갈지 결정 대기 중이다.
  • 쥠 판정 grasped: 닫힘 구간 그리퍼 최솟값 ≥ grasp_min(52). 실기 오란다 1회는 놓기 감지 + 쥠 성공, 22.7초였다.
  • 실행 기록(recorder.py): 정책 phase마다 관절값·프레임을 logs/runs/<시각>_<스킬>/에 저장한다 (episode.json 형식, 재생 데이터로 복사해 쓸 수 있음).
  • Windows 카메라 목록은 pynokhwa의 JSON 역슬래시 버그가 있어 wincam.py가 보정한다. physicalai는 NV12(비압축) 720p30을 고르므로 카메라를 USB 포트 하나에 두 대 이상 물리면 시간 초과가 난다 → 포트를 나눠 꽂는다 (허브 없이).

12. 확인된 사실 · 열린 문제

예전에 "미확인"이던 항목은 2026-10-22~23에 대부분 해소됐다.

해결된 것

  • physicalai 설치 경로·시그니처: PyPI physicalai 0.3.0, SO101은 본체(physicalai.robot.so101). 시연 노트북 .venv에 설치했다 (설계 11.6절).
  • 학습 카메라 이름: dori_dori는 tower cam / follow cam, oranda_pickup은 a / b / follow (camera_map으로 config 이름에 매핑). a/b를 서로 바꿔도 정책 출력은 같다.
  • 노트북 장치: Ubuntu 대신 Windows 11 PC가 시연 노트북이다. 정책은 CPU(GPU 컴파일 55~65초). 포트 COM5/COM6, 카메라 1·2·3.
  • 그리퍼 기준값: 실측으로 확정(빈손 49.4~50.1, 쥠 54.2~55.4, 열림 79.0 → 56.0 / 56.5 / 52 / 0.15).
  • API 모델 ID: 대화 LLM은 Claude(claude-opus-5-5) → NVIDIA(nemotron) → 규칙, STT는 로컬 Whisper → Gemini, TTS는 Gemini → Windows Heami 예비.

열린 문제 (2026-10-23 기록 · 시연 후 모두 하지 않고 종료)

  • 제어 루프 주기: 11~13 Hz (녹화 에피소드 fps 11.0 / 13.1, 학습은 30 Hz, 런타임 스텝당 약 77 ms). 의심: 카메라 3대 NV12→RGB 변환, MJPEG 스트림 인코딩, 실행 기록, 3D 트윈, CPU 경쟁. 끝내 고치지 못했다. 오란다 집기 실패의 원인 후보다 (ui.tiles·recording.enabled를 줄여 비교하는 일은 하지 않았다).
  • 카메라 시간 초과: 서버를 다시 띄울 때 "Timed out waiting for first frame"이 가끔 난다 (USB 대역폭). 다시 꽂거나 USB 포트를 나눈다.
  • 도리도리 모델: 모델은 pan이 ±1에 머물러 못 한다. 시연은 코드 도리도리(source: script)로 했다. 모델은 데이터가 적어 과적합이고 더 녹화하지 못했다.
  • 쥠 판정 거짓 실패(리뷰 I-2): 녹화 시뮬레이션에서 정지하지 않은 8개 중 7개가 grasped=False. 실기 1회는 쥠 성공이라 전체 흐름에서 빈도를 본 뒤 고칠지 정한다.
  • VLM 개수 세기: 학습하지 못했고 코드도 삭제했다. 개수 세기는 OpenCV 규칙.
  • 리뷰: OpenCV counter v2(fb6a85d)와 half 거부 규칙(27bdae2)의 opus 리뷰는 Approved with notes. 지적 사항(허용 밖 skill이면 LLM 대사도 버림, 사이클당 세기 방법 한 번 결정, half 게이지)은 0ea623b에서 반영했다.
  • homerunball 원격은 e066990까지이고 이후 로컬 커밋은 사용자가 push한다.
2026-10-25 최종 정리. 이 페이지는 위 문서들을 요약한 안내서이며, 세부 내용과 최신 결정은 각 원문(특히 설계 문서)을 따른다.
