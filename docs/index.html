과자 옮기기 로봇 문서 가이드

처음 합류한 팀원이 흩어진 문서를 빠르게 이해하도록 요약한 페이지입니다. 기준 문서는 설계 문서(2026-10-22 chat-ui-design)이며, 다른 문서와 충돌하면 설계 문서가 우선합니다.

1. 한눈에 보기

SO-ARM101 로봇팔이 여러 과자가 섞인 트레이에서 목표 과자(지금은 오란다, config.target.name으로 바꿀 수 있음)만 골라 빈 트레이로 옮긴다. 사람이 채팅이나 음성으로 작업을 시키면 일을 시작하고, 몇 번 하면 지쳐서 dori_dori(도리도리)로 일을 거부한다. 진행자가 달래거나 r 키를 누르면 다시 일하고, 마지막 과자를 옮기면 완료 멘트 후 IDLE로 돌아간다.

하드웨어는 SO-ARM101 팔로워 1대·학습용 리더 1대, 카메라 2대(외부 + 손목)이고, 2일 해커톤 프로젝트다.

2. 시연 흐름

  1. 진행자가 "이 로봇은 과자 공장 직원입니다. 오란다만 골라내요."라고 소개하고, 채팅에 "과자 옮겨줘"를 입력한다 (s 키도 같은 동작). 상태 IDLE → WORKING.
  2. 1~3회째: 로봇이 한 개씩 옮기면서 점점 투덜댄다. 3회째쯤에는 힘들다는 예고 멘트가 나온다.
  3. 4~5회째: LLM이 계속할지 거부할지 고른다 (매번 달라지는 구간).
  4. 6회째: 코드가 dori_dori를 강제한다. 로봇이 도리도리하며 거부하고 상태는 REFUSING.
  5. 진행자가 "조금만 더 해 주세요~"라고 달래거나(채팅·음성) UI 재개 버튼 또는 r 키를 누르면 count = 0으로 초기화되고 다시 WORKING.
  6. 마지막 오란다까지 옮기면(남은 0개) 완료 멘트 → DONE → 자동으로 IDLE. 트레이를 다시 세팅하면 채팅만으로 다시 시작할 수 있다.
  7. 이상 시 space 또는 UI 비상정지 → ESTOP, 해제는 restart(home_pose 복귀 후 IDLE).
시연 직전 체크, 장애 대응, 발표용 숫자는 DEMO_RUNBOOK.md에 있다.

3. 핵심 규칙 (CLAUDE.md의 절대 규칙 9개)

#규칙왜
1횟수는 코드가 센다. LLM은 프롬프트로 받은 숫자를 해석만 한다.피로도·거부 타이밍이 시연의 핵심이라 LLM의 변덕에 맡기지 않는다.
2ACT 정책 하나 = 동작 하나. 순서·횟수는 controller가 관리한다.ACT는 기억이 없어 몇 번째인지 모른다.
3LLM 출력은 허용된 값만. skill은 oranda_pickup | dori_dori | done, 채팅 intent는 상태별 허용 목록(start_task | chat | resume) 안에서만. 벗어나면 규칙으로 결정.잘못된 출력이 로봇 동작으로 이어지지 않게 한다.
4STT는 UI 🎤 누르고 말하기. 인식 문장은 채팅과 같은 경로(controller.chat).상시 청취는 발표장 소음·모터 소리·로봇 자신의 TTS 때문에 부정확하다. 같은 경로면 로직을 재사용한다.
5파인튜닝 없음. 개수 세기는 제로샷(YOLO-World 텍스트 클래스, VLM)과 OpenCV. 외부 OpenVINO 검출 모델은 같은 자리에 꽂을 수 있다.2일 안에 끝내야 하고, 학습 없이도 박스 오버레이까지 얻는다.
6physicalai / LeRobot 코어 수정 금지. 설치된 버전의 API를 확인해 그대로 사용.라이브러리를 고치면 유지가 어려워지고, 시그니처가 버전마다 다를 수 있다.
7oranda_pickup ACT는 놓기까지만. 그리퍼 "닫힘 → 열림"을 감지하면 ACT를 멈추고 코드가 lift_pose → home_pose로 복귀. 스킬 시작 전에는 항상 home_pose.복귀 구간은 매번 궤적이 달라 데이터가 적을 때 노이즈가 되고, "돌아오자마자 또 집으러 가는" 혼란도 막는다.
8외부 API는 타임아웃 필수. provider 체인이 전부 실패해도 로봇 루프는 규칙 fallback으로 계속 돈다.네트워크 때문에 로봇이 멈추면 시연이 깨진다.
9비상정지는 토크 유지. 정지 순간의 목표값을 고정해 유지한다.토크를 끄면 팔이 떨어져 과자·트레이와 부딪힌다.

4. 구조

모든 명령은 project 루트에서 실행한다. 프로세스 1개, 스레드 4종(controller 루프, uvicorn, 콘솔 키, 카메라 캡처)으로 돈다.

python -m snackbot --dry-run            # 로봇 없이 전체 흐름 + UI (http://localhost:8000)
python -m snackbot --dry-run --no-ui    # 콘솔만
python -m snackbot                      # 실제 로봇
python -m snackbot.vision tests/samples/tray_3.jpg   # 모듈 단독 테스트
python -m tools.save_pose home          # 현재 팔 자세를 home_pose로 저장 (lift도 동일)
pytest
의존 방향: server → controller → (brain, vision, skills, voice). controller는 FastAPI를 모른다. --no-ui면 server 없이 돈다. 패키지는 위치만 묶을 뿐 이 방향은 그대로다.

상태채팅 허용 intent처리
IDLE / DONEstart_task, chatstart_task → 시작 개수 정하고 사이클 시작
WORKINGchat대답만, 작업 영향 없음
REFUSINGresume, chat (M5부터 resume)resume → count = 0, WORKING
ESTOPchat대답만. 해제는 restart 명령으로만
  • phase(UI 표시용, WORKING 내부 단계): idle | counting | thinking | acting | returning | waiting_operator
  • 옮기기 실패가 max_retry(기본 2)를 넘으면 WORKING을 유지한 채 phase=waiting_operator. 재개 명령으로 다시 시도하며 count는 변하지 않는다.
  • ESTOP 후 restart는 home_pose로 천천히 복귀한 뒤 IDLE (사람이 명시적으로 다시 시작하는 쪽이 안전).

임계값은 config.yaml의 decision.safe_max: 3, force_refuse: 6, max_retry: 2.

왜 ACT가 과자를 찾는데도 개수를 세는가 (B → A)

찾아 집는 일은 ACT가 영상만 보고 한다. 개수 판정은 정확도 때문이 아니라 ACT가 못 하는 두 가지 때문이다: 언제 끝낼지(ACT는 "이제 없다"를 몰라 0개여도 허공이나 다른 과자를 집는다)와 성공했는지(count는 성공 때만 올라가고 이것이 거부 타이밍을 정한다).
B (M1, 기본)A (M3, 개선)
시작 개수채팅의 n("3개 옮겨줘") → 없으면 target.initial_count시작 전 counter로 셈
성공 판정grasped: 닫힘 구간의 그리퍼 최솟값 ≥ grasp_min (빈 그리퍼는 끝까지 닫힘)실행 전후 개수 감소. grasped는 로그용 보조
남은 개수시작 개수 − 성공 수counter 결과
한계다른 과자를 집어도 성공으로 셈. 시작 개수가 틀리면 끝 판단도 틀림모델·튜닝 필요
  • vision.chain이 비어 있으면 B, 있으면 A. A에서 counter가 전부 실패한 사이클은 그 사이클만 B로 판정한다 (멈추지 않음).
  • UI의 vision_method: B면 estimate("추정"으로 표시), A면 실제 counter 이름.
  • 성공이면 count += 1. 실패는 count에 넣지 않고 실패 멘트 후 재시도(최대 max_retry회) → 그래도 실패면 phase=waiting_operator.
LLM 출력 스키마와 검증 순서 
{"skill": "oranda_pickup | dori_dori | done", "say": "한국어 대사 1~2문장"}
  1. JSON 파싱 실패 → fallback
  2. skill이 허용 값이 아님 → fallback
  3. 가드가 강제한 skill과 다름 → 가드 결과로 덮어쓰고 대사만 사용
  4. say가 비었거나 너무 김(80자 초과) → 준비된 대사 목록에서 랜덤

시스템 프롬프트는 "투덜이 성격의 과자 공장 로봇팔"로, remaining / count / allowed / speech_text를 받아 JSON 한 줄만 출력한다. {target}은 config.target.name으로 채운다. 전문은 DECISION_LOGIC.md 5장.

채팅 의도(chat)와 키워드 fallback

채팅 입력과 STT 결과는 같은 경로(brain.chat)로 들어온다. 출력: {"intent": "start_task | resume | chat", "say": "...", "n": 3}. n은 "3개 옮겨줘"의 개수(없으면 null)다.

상태allowed intent
IDLE / DONEstart_task, chat
WORKING / ESTOPchat
REFUSINGresume, chat (M5부터. 그 전에는 chat만)

JSON 실패나 허용 외 intent면 키워드 규칙: start_task(옮겨, 집어, 시작, 일해), resume(조금만, 부탁, 힘내, 한 번만), 그 외 chat. n은 숫자 또는 한글 수사(하나·둘·셋…) 정규식으로 파싱한다.

fallback 대사 (LLM 실패 시)

준비된 대사 목록이 있다: oranda_pickup, count 3 예고, dori_dori("싫어요! 힘들어요!"), done, 실패 재시도, 재개, 잡담, 일하는 중 잡담. 목록은 DECISION_LOGIC.md 6장.

7. provider 체인

역할(brain · vision · stt)마다 provider 목록을 두고 순서대로 시도한다. 예외나 타임아웃이면 다음으로 넘어가고, 전부 실패하면 규칙 fallback으로 결정한다. 어떤 provider가 응답했는지는 사이클 로그와 UI info에 남는다. API 키가 없는 provider는 체인에서 건너뛰고 시작 시 경고한다.

8. 로봇 연동 (physicalai 런타임)

physical-ai-studio에서 학습해 OpenVINO로 내보낸 ACT를 physicalai 패키지(~0.3, 설치 후 시그니처 확인 필요)로 직접 실행한다. Studio의 RobotRuntime/Shared*는 쓰지 않는다. 정지 조건과 비상정지를 매 스텝 확인하려고 루프를 직접 돈다.

API용도
SO101(port, calibration, role="follower")connect(), get_observation().joint_positions, send_action(arr, goal_time=...), set_torque(enabled), disconnect()
UVCCamera(device, width, height, fps)RGB HWC uint8 프레임
InferenceModel(export_dir, backend="openvino", device=...)reset(), select_action(obs) (chunk 큐 내장). 입력 state (1, 6) float32, images.<cam> (학습 때 카메라 이름 그대로). 정규화가 그래프에 포함되어 출력이 곧 관절 목표값
  • 관절 순서: shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll, gripper
  • 단위: 몸통 -100..100, 그리퍼 0..100 (정규화 단위). home_pose, lift_pose, 그리퍼 기준값 모두 이 단위.
  • 정책 결과물: Studio exports/openvino/ = act.xml, act.bin, manifest.json.
  • 30fps 루프, 시작 시 정책 2개 로드 + warmup. 카메라는 캡처 스레드 하나가 소유하고 최신 프레임을 캐시한다. ACT 루프·개수 세기·/stream/front가 모두 캐시를 읽는다.
  • 카메라 이름과 캘리브레이션은 학습·녹화 때와 같아야 한다. 로봇 포트는 한 프로그램만 잡을 수 있으니 Studio 세션을 먼저 닫는다.
그리퍼 정지 조건은 "닫힘 → 열림" 전이. 홈 자세에서 그리퍼가 이미 열려 있으면 "열림 + 0.5초" 조건은 시작하자마자 걸린다. 그래서 닫힘 기준(gripper_closed_below)을 한 번 지난 뒤 열림 기준(gripper_open_above)을 open_hold_s(0.5초) 넘으면 정지하고, 안전장치로 max_time_s도 둔다. 기준값은 tools/gripper_stats.py로 데이터셋에서 정한다.
비상정지는 토크 유지. estop()은 공유 이벤트를 set해 ACT 루프·보간 이동이 다음 스텝에서 멈추게 한다. 정지 순간의 목표값을 한 번 고정해 그 값만 유지한다 (측정값을 매번 다시 보내면 중력으로 처진다). 토크는 끄지 않는다. restart → release_estop() → home_pose로 천천히 이동 → IDLE.
  • dori_dori: max_time_s(예: 6초)만큼 실행 후 home_pose로 오차 보정. 자세 이동은 관절 공간 선형 보간(steps·step_s)이며 매 스텝 estop을 확인한다.
  • 쥠 판정 grasped: 닫힘 구간 그리퍼 최솟값 ≥ grasp_min (빈 그리퍼 닫힘 값과 데이터셋의 쥠 값 사이로 정함).
ACT 데이터셋 녹화 규칙 요약 (DATASET_GUIDE)
  • 데이터셋은 동작별로 따로(oranda_pickup, dori_dori), 에피소드 하나 = 동작 한 번. "5번 옮기고 도리도리"처럼 찍으면 아무 때나 도리도리하는 정책이 된다.
  • oranda_pickup: 홈 자세에서 시작 → 섞인 트레이에서 1개 집기 → 빈 트레이에 놓고 놓자마자 녹화 종료 (복귀는 코드). 50개 이상(세트당 3에피소드 × 17~20세트), 10~15초, 카메라 2대 필수. 다른 과자도 함께 배치하고 위치를 바꾸되 트레이 위치는 고정. task 문장 "PIck up the Snack and place it in the empty tray".
  • dori_dori: 10~20개, 5~6초, 홈 복귀 포함, 리더 그리퍼는 고정. task 문장 "Shake the arm side to side to say no".
  • 녹화·학습·내보내기는 현재 physical-ai-studio UI로 한다. 문서의 LeRobot CLI 명령은 참고용.

체크리스트 전문은 DATASET_GUIDE.md 6장.
